# 数据库页加解密与 WAL

证据：C/T。来源：`src/crypto/{mod.rs,auth.rs,wal.rs}`、`src/scanner/windows/account.rs`。下述固定参数足以指导实现主库页与 WAL 恢复；主库有合成AES/HMAC检查，WAL有结构、认证及应用顺序检查，但尚无WAL与AES的端到端验证。不宣称兼容所有 SQLCipher 配置或微信版本。

## 材料与参数

接口输入为加密主库及其32字节 AES 数据库密钥 K。该 K 已经是派生结果，不能再次做256000次派生。若输入为捕获路径取得的32字节候选 R，则读取主库首页16字节盐 S，计算：

```text
K  = PBKDF2-HMAC-SHA512(password=R, salt=S, iterations=256000, dkLen=32)
SH = each byte of S XOR 0x3A
KH = PBKDF2-HMAC-SHA512(password=K, salt=SH, iterations=2, dkLen=32)
```

KH 是页面 HMAC 材料。每个数据库使用自己的 S；候选能派生多个数据库的密钥不证明它是微信所有媒体的根密钥。捕获 R 的来源机制见[密钥材料](key-material.md)。

## 主库页面布局

页面大小固定4096。保留区80字节：IV16字节 + HMAC-SHA512 64字节。页码从1开始。

| 页 | `[0,16)` | 密文范围 | IV | HMAC |
|---|---|---|---|---|
| 主库第1页 | 盐 S | `[16,4016)` | `[4016,4032)` | `[4032,4096)` |
| 主库后续页 | 密文的一部分 | `[0,4016)` | 同上 | 同上 |

认证消息为密文加 IV 再加**四字节小端页号**：第1页取 `page[16:4032] || LE32(1)`，后续取 `page[0:4032] || LE32(pgno)`。计算 HMAC-SHA512(KH, message)，与末64字节进行恒时比较。不要遗漏 IV 或把页号写为大端。

认证成功后，用 AES-256-CBC(K, IV) 解密相应密文段，**不使用 PKCS#7 去填充**。首页前16字节改写为 `SQLite format 3\0`；解出的正文放回原偏移，末80字节置零。保留 SQLite 页头中相应保留区语义，不能直接把页面压缩成4016字节。

```text
require file_size > 0 and file_size % 4096 == 0
derive KH from original encrypted page 1
for pgno = 1 .. page_count:
    require verify_HMAC(page, pgno)
    decrypt correct slice with this page's IV
    append exactly 4096 plaintext bytes to temporary output
recheck source stability
publish temporary output atomically
```

首页校验用于筛选候选材料；只有逐页认证才能发现后续页损坏。错误密钥、截断页、认证失败或源文件处理中变化时，不发布部分新结果。

## WAL 布局与有效提交

WAL头32字节，帧为24字节帧头加4096字节页面。除校验计算时的字序选择外，下列字段读取为 u32 大端。

| WAL头偏移 | 含义 |
|---|---|
| 0 | magic `0x377f0682` 或 `0x377f0683` |
| 4 | 格式版本3007000 |
| 8 | 页面大小4096 |
| 16、20 | 两个代次 salt |
| 24、28 | 头滚动校验和 |

帧头0为真实页号，4为提交后数据库页数（0表示不是提交标记），8..16为该代次 salt，16和20为帧校验和。WAL代次 salt 不用于 PBKDF2；页面认证 KH 仍从**原加密主库首页 S**派生。

校验算法以两个 u32 累加器 s0、s1 开始，溢出按模2^32处理。每8字节读取 a、b：magic尾字节82时按小端读取，83时按大端读取；依次 `s0=s0+a+s1`，`s1=s1+b+s0`。头部对前24字节从零计算。每帧沿用上一帧累加器，先覆盖帧头前8字节，再覆盖页面4096字节。存储的校验值仍按大端读取。

顺序扫描连续有效帧：页号非零、代次盐匹配、滚动校验正确。第一次失配就停止；不能跳过坏帧寻找后面的“有效帧”。记录此前最后一个非零提交页数对应的帧位置；忽略其后未提交帧和不足整帧的尾部。当前项目限制页号和提交页数≤1,000,000，合法但超限也显式报错。

## WAL 页面认证及应用

对选中提交前缀内的**每一帧**认证，包括稍后会被覆盖或截断的帧。WAL页面采用完整密文布局 `[0,4016)`，即使真实页号为1也不跳过16字节；认证附加的仍是真实页号。没有使用盐首页布局的回退猜测。

认证全部成功后复制旧明文主库到临时结果，按帧顺序把解出页面写到 `(pgno-1)*4096`。每个提交标记都按其页数截断临时结果，最后按最终提交页数设置长度。不能只在最后截断：中间收缩后再次扩容会暴露已经删除的旧页。核对主库及 WAL 的大小/修改时间后才发布。元数据稳定检测是项目保障，不等于操作系统级一致快照证明。

## 合成验证与边界

用人工 R（例如32字节递增序列）与 S（16字节递增序列）生成 K/KH，自行构造两页，AES-CBC加密后按上述消息布局生成 HMAC。验证恢复字节、翻转第2页密文拒绝、替换 IV拒绝、变更页号拒绝。构造“提交A→未提交B”时只能应用A；坏帧后即使出现非零提交数也不能恢复继续。

主库导出命令有只取主文件、不合并实时 WAL 的路径；因此导出时间不等于最后消息时间。不要把本章描述的 WAL 能力泛化到每个导出入口。SQLite可打开也不能替代加密认证或记录完整性校验。

## 已运行的公开WAL合成向量

运行`python tools/check_wal.py`可重建向量并检查结果；[向量描述与摘要](../evidence/wal-vectors.json)记录每帧的`[真实页号,提交页数,人工内容标签]`、校验字序、总字节数、SHA-256与预期选中前缀。生成器完全自包含，不读取文件或账号材料。

5组固定向量分别为：无提交、提交后未提交尾帧、大端校验、同页后写覆盖、收缩后增长。后者从人工页面标签`[7,8,9]`开始，页1提交收缩到1页，然后页3提交增长到3页，必须得到`[10,0,30]`，不能重新暴露旧页2标签8。

共15项检查还覆盖校验和算术锚点、半帧尾部、坏帧后停止、代次salt不匹配、损坏/截断头、被覆盖帧的坏HMAC、真实页号绑定、误用WAL salt及超限。先认证全部选中帧，再应用；坏HMAC时旧输出标签保持不变。

**验证边界：** WAL载荷是人工构造的“密文形状”字节并计算真实HMAC；本脚本不进行AES解密。应用阶段用标签代表已经解密的页面，只验证覆盖与截断顺序。它是独立文档检查，不调用生产Rust实现，也不是真实微信证据。主库AES检查不能据此升级为WAL端到端验证。
